# CipherCam — benchmark results

Generated by `npm run bench` on 2026-11-01 — Intel(R) Xeon(R) Processor @ 2.10GHz (4 threads), Node.js v22.23.4, linux.
1000 frames of 160×120 grayscale (19,200 bytes) per mode, same `shared/` code as the browser.

**MITM (AES-GCM):** Bob accepted 100/100 frames that Eve decrypted and re-encrypted. The safety numbers were `0724 9681 7605` (Alice) and `7003 9299 8705` (Bob): **MISMATCH** — only this human check reveals Eve.

**Browser frame rate:** see `e2e-fps.json` (measured by `npm run e2e` with all three Stage panels open).

## What the numbers say

1. **Speed is not the problem.** Even the slowest mode needs about 0.73 ms to encrypt a frame, far below the 100 ms budget of a 10 fps call. AES-GCM costs 0.10 ms vs 0.19 ms for plain CTR, so the secure mode is essentially free. (ECB runs in the pure-JavaScript aes-js library, so it is the slowest here; Web Crypto modes use native AES.)
2. **Only ECB leaks.** The leak meter reads 89.6 % for ECB (the same as no encryption, 89.6 %), because identical 4×4 tiles give identical ciphertext blocks. Every randomized mode reads 0.0 %. Note that the buggy `ctr-reuse` mode also reads 0.0 %: inside ONE frame its keystream still looks random. Its flaw only appears ACROSS frames (C₁ ⊕ C₂ = P₁ ⊕ P₂), which is why Eve needs the keystream-recovery view to exploit it.
3. **Encryption is not integrity.** With no MAC, 0 % of bit-flipped and 0 % of replayed frames are rejected (CBC turns the stamp into garbage but still shows it). With CTR+HMAC or AES-GCM, 100 % / 100 % of tampered frames and 100 % / 100 % of replayed frames are rejected, for an overhead of only 48 / 28 bytes per frame.
4. **Nothing in the frames stops a MITM.** Bob accepted every re-encrypted GCM frame; key authentication (the safety-number check) is the only defence.
